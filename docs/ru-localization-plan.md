## 1. Цель

1. **Русскоязычный интерфейс** — риббон, диалоги, чат-панель, справка.
2. **Понимание русских команд** — распознавание намерений и маршрутизация инструментов на русском языке.
3. **Ответы на русском** — модель отвечает по-русски независимо от языка входных данных и внутренних промптов.
4. Сохранение работы в закрытом контуре (offline), включая локальную справку.

## 2. Критерии приёмки

- [ ] 100% видимых элементов UI на русском (риббон, все диалоги, чат-панель, справка).
- [ ] Набор из ≥30 русских команд выполняется без подсказок (intent + tool routing).
- [ ] 100% ответов на русском на тест-наборе, включая случаи, когда документ/контекст на другом языке.
- [ ] Китайские и английские команды продолжают работать (обратная совместимость матчинга).
- [ ] Справка открывается локально, без обращения к `officeso.cn`.
- [ ] При отключённой сети всё ядро работает против внутреннего OpenAI-совместимого endpoint.
- [ ] Внутренний endpoint с самоподписанным сертификатом (или сертификатом внутреннего CA) работает во всех каналах: чат, streaming, ReAct/tool-loop, проверка моделей, embeddings, FIM-автодополнение, MCP.
- [ ] `platform`-идентификаторы, ID инструментов и ID контролов риббона не изменены.

## 3. Ключевая проблема: языковой дрейф модели

Слабые модели склонны отвечать на языке промпта и/или команды. Оставлять китайские промпты нельзя — при русском вводе ответ может уйти в китайский. Поэтому:

1. Все системные промпты переводятся на русский.
2. В **каждый** слой промптов добавляется «языковой контракт»:

   > Отвечай только на русском языке. Не переключай язык, даже если входные данные, документ, имена файлов или предыдущие сообщения на другом языке. Цитаты и код сохраняй как есть.

3. Описания инструментов (tools) и навыков (skills) переводятся на русский — они попадают в контекст модели и влияют на язык.
4. Опциональный guardrail (P4): пост-проверка ответа на преобладание кириллицы; при нарушении — повторный запрос с усиленной инструкцией.

### 4.7 Доверие самоподписанным сертификатам провайдера (P3, offline, блокер)

Внутренний OpenAI-совместимый endpoint в закрытом контуре почти всегда отдаётся по HTTPS с самоподписанным сертификатом или сертификатом внутреннего CA. Сейчас это не поддержано: все HTTP-клиенты используют стандартную валидацию цепочки, поэтому запрос падает с «Could not establish trust relationship». Текущий код задаёт только `ServicePointManager.SecurityProtocol = Tls12` и нигде не настраивает проверку сертификата.

Факт из целевой среды: работоспособность достигалась глобальной переменной окружения ОС `NODE_TLS_REJECT_UNAUTHORIZED=0`. Она действует только на Node.js-процессы (включая Node-based MCP-серверы, которые наследуют окружение родителя) и полностью отключает и проверку цепочки, и проверку имени хоста. На .NET, через который идут все запросы плагина (`HttpClient` в `AiGateway`, `HttpStreamService`, `HttpClientPool`), она не влияет никак — значит реализация из этого раздела обязательна, полагаться на env var нельзя. Глобальную переменную не считать решением: она ослабляет TLS сразу для всех Node-приложений на машине; в плагине доверие должно быть привязано к конкретному провайдеру и по умолчанию выключено. Поскольку обходной путь отключал и проверку имени, pinning только по цепочке CA недостаточен — реализуем семантику «принять любой сертификат» (pinning — вне первой итерации).

Точки TLS-терминации (каждую надо покрыть, иначе часть каналов продолжит падать):

| Канал | Файл | Клиент |
|---|---|---|
| Центральный пул | `ShareRibbon/Utils/HttpClientPool.vb:11` | `New HttpClient()`; через него — streaming, список моделей, проверка подключения, embeddings, FIM, перевод, `WebDataCapturePane` |
| Не-streaming чат (Agent/Loop) | `ShareRibbon/Services/Ai/AiGateway.vb:41` | отдельный `Shared HttpClient` |
| Office completion | `ShareRibbon/Controls/Services/OfficeCompletionService.vb:15` | отдельный `Shared HttpClient` |
| Совместимость | `ShareRibbon/Common/LLMUtil.vb:100` | собственный `HttpClientHandler` |
| Совместимость | `ShareRibbon/Controls/Services/UtilsService.vb:238` | собственный `New HttpClient()` |
| MCP (если сервер по HTTPS) | `ShareRibbon/Mcp/StreamJsonRpcMCPClient.vb:29` | отдельный `HttpClient` |
| Проверка в UI | `ShareRibbon/Config/ModelApiClient.vb:30`, `ShareRibbon/Config/ConfigApiForm.vb:1894` | через `HttpClientPool` |

Действия:

1. Ввести единый фабричный метод `CreateHttpClientHandler()` в `ShareRibbon/Utils/` и перевести на него все точки из таблицы (в `HttpClientPool` — создавать handler в `GetOrAdd`). Никаких «своих» `New HttpClient()` вне фабрики.
2. Добавить в `ConfigItem` (`ShareRibbon/Config/ConfigManager.vb`) один флаг доверия: `allowInsecureTls As Boolean` (по умолчанию `False`). Pinning по `caCertPath`/отпечатку в первую итерацию не делаем — по решению достаточно режима «принять любой» для конкретного провайдера. Флаг сохранять/загружать вместе с провайдером в `office_ai_config.json` и явно переносить в `MergeConfigurations` (иначе сбросится при рестарте).
3. Логика проверки: при `allowInsecureTls = True` — принять любой сертификат, **включая несовпадение имени хоста**; иначе — обычная валидация. Реализовать через `HttpClientHandler.ServerCertificateCustomValidationCallback` только для клиента конкретного провайдера, без глобального отключения проверки.
4. В `ConfigApiForm.vb` (форма настройки провайдера) добавить чекбокс «Разрешить самоподписанный сертификат», с предупреждением о снижении уровня безопасности и понятной ошибкой при недоверенном сертификате. Кнопка проверки подключения должна использовать ту же политику.
5. Запретить глобальное `ServicePointManager.ServerCertificateValidationCallback = Function(...) True`: если оставлять как временный fallback для кода, который не переведён на фабрику, — только при включённом флаге, с логированием хоста (без секретов и без содержимого запросов).
6. WebView2: чат-панель не ходит в провайдер напрямую (запросы идут из хоста), но при навигации на внутренние HTTPS-ресурсы справки/виртуального хоста учесть `CoreWebView2.ServerCertificateErrorDetected`; предпочтительно оставить локальные ресурсы на `http`/виртуальном хосте `officeai.local`, чтобы не трогать сертификаты WebView2.
7. Не логировать и не сохранять приватные ключи; при включённом флаге в лог писать только хост и факт ослабленной проверки, без содержимого запросов и ключей.
8. Node-based MCP-серверы уже принимают `EnvironmentVariables` per-connection (`StreamJsonRpcMCPClient.vb:86-87`, UI `StdioConfigForm.vb`). При включённом флаге доверия подставлять `NODE_TLS_REJECT_UNAUTHORIZED=0` только процессу этого MCP, а не глобально на всю машину — текущий глобальный обходной путь следует убрать из целевого контура.
9. Версия TLS endpoint заранее неизвестна, а сейчас везде жёстко зашит `ServicePointManager.SecurityProtocol = SecurityProtocolType.Tls12`, который на .NET Framework 4.7.2 ограничивает соединение сверху версией 1.2. Заменить жёсткий `Tls12` на `SecurityProtocolType.SystemDefault`, чтобы версия определялась политикой ОС/Schannel. Если на месте выяснится, что endpoint принимает только TLS 1.3 — .NET Framework 4.7.2 его не поддерживает: потребуется поднять target framework до 4.8 (плюс поддержка TLS 1.3 в Windows 10 1903+/Server 2019+) либо терминировать TLS локальным reverse-proxy с TLS 1.2. Это проверяется на месте (например, `openssl s_client -connect host:443 -tls1_3` / `-tls1_2`) до начала работ.

Проверка: поднять локальный HTTPS-прокси с самоподписанным сертификатом перед OpenAI-совместимым API; с выключенным флагом — понятная ошибка, с включённым — успешные чат, streaming, tool-loop, проверка моделей, embeddings, FIM и MCP. Отдельно на реальном endpoint зафиксировать поддерживаемую версию TLS (1.2 / 1.3) до начала работ — см. пункт 9.

## 7. QA и тестирование

- Целевые модели контура: qwen3.5 397B и qwen3.6-35B — обе хорошо поддерживают русский, что делает критерий «100% ответов на русском» реалистичным.
- Доступа к боевому стенду на момент разработки нет; проверка выполняется по факту развёртывания. Поэтому синтетические локальные проверки (HTTPS-прокси, тестовый OpenAI-совместимый endpoint) обязательны.
- Скрипты репо: `scripts/run-golden-l0.ps1`, `scripts/smoke-*.ps1`, `scripts/run-code-checks.ps1`.
- Ручные сценарии: контрольный список ≥30 русских команд по доменам из §4.2, с проверкой языка ответа.
- Регресс: те же действия китайскими и английскими командами — должны по-прежнему срабатывать.
- Offline-тест: отключить сеть, оставить только внутренний endpoint; проверить чат, агент, память, справку.
- Метрики: доля ответов на русском = 100%; доля успешных RU-команд ≥ целевой (задать после первого прогона).

| Конфликты при обновлениях upstream | Минимизировать правки, вести список изменённых файлов, отдельная ветка |
| Потеря функциональности из-за перевода логических строк | Не заменять логические ключи, только добавлять русские |
| Кодировка | Все файлы UTF-8 (с BOM для `.vb`), проверять после массовых правок |
| Внутренний endpoint с самоподписанным сертификатом не работает | Единая фабрика HTTP-handler, настройка доверия на провайдера, pinning внутреннего CA (§4.7); не отключать проверку безусловно |
| Ослабление TLS течёт в облачные сценарии | Флаг доверия только per-provider и по умолчанию `False`; облачные пресеты не наследуют настройку |
| Endpoint принимает только TLS 1.3, а .NET Framework 4.7.2 его не поддерживает | Проверить версию TLS на месте до начала работ; при 1.3-only — подъём target framework до 4.8 или локальный TLS-терминирующий reverse-proxy с TLS 1.2 (§4.7, п.9) |

## 9. Инструменты автоматизации

1. Скрипт извлечения CJK-строк из `.vb`/`.js`/`.html` в CSV (строки, файл, номер) для перевода.
2. Скрипт обратной подстановки с чёрным списком logic-строк (§4.2) и защищённых идентификаторов (§5).
3. Проверка, что не тронуты `platform`, ID инструментов, ID контролов.
4. Журнал изменённых файлов для переноса на новые версии upstream.

## 10. Артефакты

## 11. Сборка и установка в закрытом контуре (напоминание)

- MSI собирается на подключённой машине (Visual Studio + VSTO workload + *Microsoft Visual Studio Installer Projects*), NuGet — через локальный фид/предварительный restore.
- Офлайн-предпосылки: .NET Framework 4.7.2, VSTO Runtime (`vstor_redist.exe`), WebView2 Runtime (Fixed Version/offline), Office 2016+ или WPS.
- Подпись VSTO-манифестов своим сертификатом (`build/SignArtifacts.ps1`, `OFFICE_AI_SIGN_PFX` / `_CERT_THUMBPRINT`) + Trusted Publishers через GPO; XLL — подпись или Trusted Location.
- Сертификат внутреннего AI-endpoint (самоподписанный или внутреннего CA) — не путать с сертификатом подписи манифестов: первый нужен для доверия TLS при запросах (§4.7), второй — для доверия VSTO/XLL.
